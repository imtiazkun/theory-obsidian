# theory.md — App Workflow (LLM reference)

This file describes how the theory.md Obsidian plugin works. It is written so an LLM can reason about the app. Each step lists its trigger, what it checks first, what it does and what comes out. The source of truth is the code in `src/`. If this file and the code disagree, the code wins.

## 1. One-paragraph summary

theory.md is a desktop-only Obsidian plugin (plugin id `theory-md`). Humans write a **theoretical model** of a software system as notes in an Obsidian vault. The vault is a git repository. Humans **commit** changes to the model as signed git commits. **Compile** sends every commit made since the last compile to the Claude Code CLI. Claude Code then changes the code in a separate **project folder** to match the model. Claude returns a structured **compile report** (summary, changes, questions, problems), which the plugin shows in Obsidian. The AI never writes to the model.

## 2. Glossary

| Term | Meaning |
| --- | --- |
| Vault | The Obsidian vault folder. It holds the model and is its own git repo, on branch `main`. |
| Model / theoretical model | The Markdown notes and assets in the vault. Humans write them. Read-only for the AI. |
| `Index.md` | Entry note at the vault root. Opened on app launch. |
| `instruction.md` / `instructions.md` | File at the vault root with the human-only rules and the writing syntax rules. For humans; not sent to Claude and not required for compile. |
| Model folder | A folder at the vault root named exactly like a repository in the project folder. Its notes describe that repository only. It has its own `index.md` and `instructions.md`; that `instructions.md` holds rules for Claude about the repository and is sent (only the root one isn't). |
| Issue | A GitHub issue a compile creates in one code repository. It says what to build and why, and lists the rule IDs it covers (its acceptance criteria). Kept in the report as an `IssueRecord` (`src/plan.ts`). |
| Epic | A GitHub issue labelled `epic` whose native sub-issues are a compile's issues, in build order. A compile plans one when its work spans several repositories or intents. |
| Build | Turns one compile's issues into code (W12). The only step that changes code. |
| Compile branch | A branch a build makes in a code repository, named `theory/…`: an issue branch `theory/{issue number}-{short name}` or an epic branch `theory/epic-{epic number}-{short name}`. Open until it is merged into its base or its pull request is closed. |
| Project folder | Folder that holds the code. It is one git repo, or a folder whose direct subfolders are git repos. Claude runs here (`cwd`). |
| Revision | A git commit in the vault repo. |
| Last compile marker | Git tag `theory/compiled` in the vault repo. It points at the last compiled commit. |
| Pending revisions | Commits in `theory/compiled..HEAD`. On the first compile (no tag yet), all commits up to `HEAD`. |
| Snapshot | A read-only copy of the vault at `HEAD`, made in a temp folder (`$TMPDIR/theory-model-*`). Claude reads the model from here. It leaves out the files never sent to Claude (`NOT_SENT` in `src/compile.ts`): dot folders, hidden folders, hidden notes (name starts with `_`, like `_welcome.md`) and `Instructions.md`. |
| Hidden folder | A folder whose name starts with `_`, at any depth, like `_templates`. Committed, but never sent to Claude. |
| Dot folder | A folder whose name starts with `.`, at any depth, like `.obsidian/` or `.comments/` (`DOT_FOLDERS`, `isInDotFolder`). Never sent to any agent, never counted as a change (`changedFiles`), left out of the vault check, and a revision that changes only dot folders is never pending (`pendingRevisionCount`, `revisionsBetween`). theory.md commits `.comments/` itself; git ignores `.obsidian/`. |
| Compile report | JSON record of one compile run. Kept in plugin data, never in the vault. |
| Plugin data | `.obsidian/plugins/theory-md/data.json`. Holds the settings and the last 20 reports. Git ignores it. |
| Anchor | Where a problem sits in the model: `{path, heading?, quote?}`. Claude proposes it, and the plugin checks it against the snapshot before keeping it. |
| Realized | Front matter `realized: false` marks a note as written ahead of the code. If the key is missing, the note counts as realized. Engineers set it with a box in the note header. |
| Failure overlay | Highlights and a banner the plugin draws on notes that a failed compile points to. Display only: it never edits a note. |

## 3. Actors and components

- **Engineer** (human): edits notes, commits, clicks Compile, reads reports, answers questions by editing the model.
- **Plugin** (`src/main.ts`, class `TheoryPlugin`): wires commands, views, buttons and events, and holds the compile lock.
- **Git** (run as a subprocess through `git()` in `src/vault.ts`): stores the model's history, the marker tag, diffs and snapshots.
- **Claude Code CLI** (run as a subprocess in `src/compile.ts`): reads the snapshot, edits the project folder, runs the allowed commands and returns structured output.
- **ACP agent** (optional, run as a subprocess in `src/acp.ts`): when the Compile or Build row's agent is "ACP agent", that task runs the engineer's own Agent Client Protocol agent (e.g. `gemini --experimental-acp`) instead of Claude Code. Expand and Writing (Suggest, commit messages and pull request bodies) always use Claude Code. The plugin never installs an agent.

## 4. Settings

| Key | Default | Used by |
| --- | --- | --- |
| `fullName` | `""` | Saved by older versions only. Never signs; the Author section offers to write it into the vault's git config when git lacks a name or email (CFG-37). |
| `email` | `""` | Same as `fullName`. |
| `projectFolder` | `""` | `cwd` for Claude Code. Compile won't start without it. |
| `claudeCommand` | `"claude"` | CLI binary name or absolute path. Used by every task whose agent is Claude Code, and always by Expand and Writing. |
| `tasks` | see below | One row per task: `compile`, `build`, `expand`, `writing` (commit messages, pull request bodies, Suggest) (CFG-41). `src/agent-rows.ts`. |
| `tasks.compile` | Claude Code, `""` everywhere | `agent` (`"claude"` or `"acp"`), `agentCommand`, `agentModel`, `agentThinkingLevel` (ACP only, matched against the agent's choices by value or name, kept apart from `model`/`effort`), `model` (`--model`: `fable`, `opus`, `sonnet`, `haiku`; `""` passes nothing), `effort` (`--effort`: `low`, `medium`, `high`, `xhigh`, `max`; `""` passes nothing). | `tasks.build` | `agent: "same"`, `model: "same"`, `effort: "same"` | Same fields as Compile's. `agent: "same"` follows Compile's whole row. With its own agent, `model`/`effort` of `"same"` follow Compile's one by one. An ACP build won't start while its `agentCommand` is empty. |
| `tasks.expand`, `tasks.writing` | `model: "same"`, `effort: "same"` | Claude Code's model and effort only; never an agent (CFG-43). `"same"` follows Compile's field. |
| `permissionMode` | `"acceptEdits"` | Passed to `--permission-mode`. Options: `acceptEdits`, `auto`, `bypassPermissions`. Claude Code builds only; hidden when Build's agent (after following Compile) is ACP. |
| `allowedTools` | `"Bash(git *)"` | Passed to `--allowedTools`. Space-separated permission rules. Claude Code only. |
| `showCompileButton` | `true` | Shows or hides the floating bar. |
| `pullAutomatically` | `true` | Pull on launch, on focus and on the timer. Pull now and the pull before a compile run either way. |
| `pullInterval` | `5` | Minutes between timer pulls: 1, 5, 15 or 30. |
| `pullCodeRepos` | `true` | Each pull also fetches the project folder's repositories with an upstream and fast-forwards the safe ones. |

Remote is a setting too, but it isn't in plugin data: it is the vault's `origin` in its git config. When the vault has an `origin`, the setting shows its URL as plain text with no field, and says to run `git remote set-url origin <url>` in the vault to change it. Without one, Save runs `git remote add origin <url>`, then a pull. Save never replaces or removes a remote. It refuses an empty URL, spaces, a leading `-` and a password or token in an https URL.

## 5. Lifecycle state machine (per vault)

```
UNCONFIGURED ──(Setup vault)──► VAULT_READY ──(set projectFolder)──► COMPILE_READY
                                                                         │
            ┌──────────────── edit note ◄───────────────────────────────┤
            ▼                                                            │
         DIRTY ──(commit)──► PENDING (n > 0 revisions) ──(Compile)──► COMPILING
                                                                         │
                       ┌─────────────────────────────────────────────────┤
                       ▼                   ▼                    ▼
                  SUCCEEDED             FAILED              CANCELLED
              (marker → HEAD)       (marker → HEAD)      (marker unchanged)
```

Compile button states (`src/compile-button.ts`, `readState`), checked in this order:
1. `hidden`: the vault isn't set up, or the button is turned off.
2. `running`: a compile is in progress. While a permission card waits, it says "Claude is asking (1:47)", counting down with the oldest card, and clicking it opens the report at that card.
3. `setup`: no project folder is set.
4. `ready(pending)`: there are pending revisions. Shows a badge with the count, in the accent colour.
5. `failed`: no pending revisions, and the newest report failed.
6. `idle`: nothing to do.

## 6. Workflows

### W1. Plugin load (`onload`)
1. Load the settings and reports from plugin data. Any report still marked `running` becomes `failed` with the problem "Obsidian closed before this compile finished."
2. Register the commands `setup-vault`, `show-commit-history`, `compile`, `show-compile-report`, `commit-current-note`, `show-repositories` and `pull-now`, plus a ribbon hammer icon (Compile), a ribbon Repositories icon and a status bar item.
3. When the layout is ready: open `Index.md` (only on app launch, not when the plugin is turned on mid-session), add the history view to the right sidebar, sync the commit buttons and attach and refresh the compile bar. On launch, pull (W14) and start the pull timer.
4. Event hooks: vault `modify/create/delete/rename`, workspace `layout-change/file-open` and window `focus` re-sync the buttons and the pending count (debounced).

### W2. Setup vault (command "Setup vault")
- **Check first:** the vault isn't already a git repo (no `.git`). Git runs and has a name and email (`gitIdentity`: the vault's `--local` config, else `--global`). Otherwise it fails with a notice.
- **Actions:** write the starter files from `src/starter.ts` if the root doesn't already have them under any name, ignoring case: `Index.md` ("Manifesting <vault name>"), `Instructions.md` (the human-only rules and the doctrine, skipped if `instruction.md` or `instructions.md` exists), `_templates/index.md` (the model folder index headings) and `_templates/instructions.md` (the line pointing at the root Instructions). Then, when the root has `Welcome.md` (ignoring case) and no `_welcome.md`, replace its text with the welcome text (`WELCOME_TEXT` in `src/starter.ts`) and rename it to `_welcome.md`; it is not a starter file, so Create missing files never writes it back. Then `git init -b main`, then add the missing lines to `.gitignore` (`.DS_Store`, `.trash/`, `.obsidian/`), then `git add -A`, then `git commit --allow-empty -m "Initial commit"` signed with the author.
- **Output:** the vault is a git repo whose initial commit includes the starter files and the welcome note. The UI refreshes and `_welcome.md` opens when setup wrote it, `Index.md` otherwise.
- **Create missing files** (settings, when the vault is set up but `missingStarters` finds starter files or `.gitignore` lines missing): checks the author, writes only the missing files and lines with the same starter text, never changes a file that exists, and commits only what it wrote as "Add missing starter files". The check runs each time the settings tab opens and after the button runs; nothing is stored.

### W3. Edit and commit
- **Trigger:** the commit button in a note's header (marked `is-dirty` when the note has changes), the commit button in the floating bar, or the command "Commit current note".
- **Check first:** the note is in the list of changed files (`git status --porcelain -z --untracked-files=all`). If not, the notice "No changes to commit in this note." The floating commit button commits the active note when it has changes, else every changed file, else shows "No changes to commit".
- **Commit page:** opens in a new tab, never a modal; only one page for new changes is open, and another commit brings it to the front. It lists every changed file with a checkbox, its path and how it changed (modified, new, deleted, renamed). A commit from a note ticks only that note; from the floating bar with no note changed, every file. Under each file its diff from `git diff HEAD -U3` (new untracked files through `git diff --no-index /dev/null`), removed lines red, added green, unchanged stretches between hunks folded into "{n} unchanged lines". Above a note's diff, "Adds X. Changes Y. Removes Z." from the bold rule IDs before and after. A rename shows "{old} → {new}"; a file that isn't text shows only its name and kind. The diff is raw text set with `setText`, and refreshes when a file changes. The message box starts empty with the placeholder "Say why. Git already shows what changed."; Commit stays disabled until it holds text and a file is ticked. "Signed as Name <email>". Cmd/Ctrl+Enter commits; Cancel closes the page and discards the message.
- **Generate (sparkle):** the uncommitted diff of the ticked files (tracked files against `HEAD`, new files whole, minus dot folders, hidden folders, hidden notes and `Instructions.md`, cut at 50,000 characters) goes on stdin to `claude -p --output-format json --no-session-persistence --tools ""`, run in the temp folder, with Edit/Write/NotebookEdit denied on the vault, and the Writing row's `--model` and `--effort`. While Claude writes, the sparkle blinks (fades out and back in about once a second); it never spins and no bar shows. The answer replaces the message. It sends uncommitted text, but never compiles it. On failure: "Couldn't generate a message: {reason}".
- **Actions:** `git add -A -- <ticked paths>` (a deletion that is already staged is skipped, since git refuses its path) then `git commit -m <msg> -- <ticked paths and the old side of a staged rename>`, so nothing else that is staged slips in. It uses `-c user.name/-c user.email` with the identity `gitIdentity` reads, so what the settings and the page show is what signs. With no name or email the notice is "Set your name and email in git first. theory.md settings show how." and nothing is committed.
- **Push:** straight after, `git push --no-tags origin refs/heads/main:refs/heads/main` with prompts off. Never forced; the `theory/compiled` tag stays local. Every other commit the plugin makes (comments, missing starter files) pushes the same way. Pushes run one at a time.
- **Output:** the page closes, and the notice "Committed and pushed {shortHash}"; "Committed {shortHash}" without an `origin`; "Committed {shortHash}, but couldn't push: {reason}" when the push fails (the commit stays, and the sync status counts what isn't pushed); "Committed {shortHash}, but couldn't push: the remote has new revisions. Pull with rebase in git, then push." when the remote moved. The buttons, the pending count, the sync status and the history view refresh.
- **Past commits:** clicking a commit in commit history opens it read-only on the Commit page, in its own tab that the next click reuses: full message, author, date, short hash, then every file the commit changed with its own diff against its first parent (the empty tree for the first commit), the clicked note first. No checkboxes, message box or Commit button.

### W4. Compile (the core pipeline)
**Trigger:** the compile button, the ribbon hammer or the command "Compile".

**Phase A: checks in `main.ts`** (if one fails, it shows a notice and does nothing else)
1. If a compile or build is already running (or starting), show "A compile or build is already running." and open the report. This is an in-memory lock, one compile or build per app.
1a. Pull the vault and the code repositories (W14), even with automatic pulls off. A sync needed, waiting revisions or a repository that is behind and can't fast-forward stops the compile with "Compile failed: …". A failed fetch shows "Couldn't reach the remote, so this compile uses the local vault and code." and carries on.
2. The vault must be set up.
3. Count the uncommitted files and warn that they aren't part of this compile. Only committed revisions are compiled.

**Phase B: start-up in `startCompile`** (if one of these throws, the compile doesn't start and the marker doesn't move)
4. The project folder must be set and must exist.
5. `head` = `git rev-parse HEAD`. If there are no commits, it errors.
6. `from` = the commit the `theory/compiled` tag points to, or `null` if there is no tag.
7. If `from === head`, or every revision in `from..head` changes only dot folders, it throws `NothingToCompileError` ("Every committed revision is already compiled.").
7a. Every repository in the project folder must have a clean working tree (`git status --porcelain`), else "These repositories have uncommitted changes: {repos}. Commit or stash them first."
7b. GitHub (`requireGitHub`, with the `GitHub` interface in `src/github.ts`; tests pass a fake): `gh` must be logged in ("Log in to GitHub first. Run gh auth login in a terminal."), every repository must have a GitHub `origin` ("These repositories have no GitHub origin: {repos}."), and the GitHub Project setting must be set ("Choose the GitHub Project in theory.md settings first.") and reachable with `gh project view` ("Couldn't reach the GitHub Project {url}: {reason}").
8. `revisions` = `git log --reverse from..head -- <DOT_FOLDERS>` (hash, author, ISO date, subject), so revisions that change only dot folders aren't listed.
9. `diff` = `git diff --stat --patch <from or EMPTY_TREE> head -- <NOT_SENT>`, cut at 200,000 characters. `notes` = the `.md` files changed in that range (`git diff --name-only`, same pathspecs), kept as suspects for the overlay. `NOT_SENT` excludes dot folders, hidden folders, hidden notes and `Instructions.md`.
10. Snapshot: `git archive head -- <NOT_SENT>` into a new temp folder, extract it, then `chmod -R a-w`.
11. Record the guards: a SHA-256 hash of the snapshot tree, and the vault's working-tree state (path → mtime, or "deleted").
11a. Read each repository's model-folder `instructions.md` from the snapshot (matched ignoring case) for the prompt.
11b. Record each repository's HEAD, branches and working tree, to check afterwards that the compile changed none of them (CMP-69). A compile never makes a branch, a commit or a push.
11c. **Recompile** (`options.recompile`, an earlier report; CMP-76). `from` for steps 8 and 9 (revisions, diff, suspect notes) is that report's `fromCommit`, not the marker, so they cover its revisions and every pending one; the new report's `fromCommit` is the same, and `recompileOf` is the earlier report's id. `openEarlierIssues` asks GitHub (`issueState`) about each of its issues that has a number and wasn't discarded, and keeps the open ones for the prompt and `readPlan`; when GitHub can't answer, the compile can't start. The pending check still uses the marker.

**Phase C: run Claude Code**
12. Make the report `{status: "running", fromCommit, toCommit: head, revisions, …}`, add it to the front of `reports` (keep 20), save, open the report tab and show "Compiling…" in the status bar.
13. Start `claudeCommand` with `cwd = projectFolder` and these arguments (`claudeArgs`, `startSession`):
    - `-p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio --verbose --no-session-persistence`
    - `--permission-mode dontAsk --tools Read,Glob,Grep --strict-mcp-config`: a compile only reads (CMP-13)
    - `--add-dir <snapshot>`
    - `--json-schema <COMPILE_SCHEMA>` (fields: `status`, `summary`, `plan{epic?{title, body, rules[], shortName, continues?, changed?}, issues[{repo, title, body, rules[], shortName, continues?, changed?}]}`; `continues` is the number of the earlier issue it continues in a recompile, `changed` the CMP-79 sentence, `questions[{question, notes[], anchors?[{path, heading?, quote?}]}]`, `problems[{problem, anchors[{path, heading?, quote?}]}]`)
    - `--disallowedTools Edit/Write/NotebookEdit(//<vault>/**)` and the same for `//<snapshot>/**`, then `Edit Write NotebookEdit MultiEdit Bash`
    - `--model <model>` and `--effort <effort>` when they aren't empty. They're fixed when Claude Code starts, so a running compile keeps them.
    - `--allowedTools Read Glob Grep`. The Permission mode and Allowed commands settings apply to builds only.
14. ### W12. Build (`src/build.ts`)
- **Trigger:** the report's Build button (on a compile that created issues), "Build them now?" after a compile, or the command "Build", which builds the newest such compile. It shares the compile lock (`buildRun` in `main.ts`).
- **Checks, in order** (none failing changes anything; each shows "Build failed: …"): the pull before a compile (W14), with "build again" in its messages; Claude Code found (`--version`), or the ACP agent command set; `requireGitHub` as in step 7b, for the repositories with an issue; no uncommitted changes in those repositories; each one's default branch (`origin/HEAD`, else `main`, else `master`) fast-forwarded to its upstream as the last fetch saw it, or "{branch} in {repo} and origin/{branch} both have new commits. Pull with rebase in git, then build again."; no open work from another compile's build ("Finish the open work in {repo} first: {branch or pull request}."): a pull request in any other report that `gh` still calls open or draft, or an epic branch that still exists, isn't merged into its base and whose pull request isn't merged or closed. The compile's own work never counts: it is continued. A closed issue no build of this compile built is skipped: "Skipped {repo}#{number}: the issue is closed."
- **Continuing (BLD-27):** building a compile built before reuses its `report.build` record and epic branch name in every repository (the local branch, else `origin`'s, else made from the default branch), and each issue's branch that still exists (locally, else from `origin`). Built issues keep their state; only issues still open with no open pull request are built, in plan order. When nothing is left, `startBuild` throws `NothingLeftError` before changing anything, and the notice is "Every issue of this compile is built." (not a failure).
- **Snapshot:** `git archive` of the compile's `toCommit`, read-only, with the snapshot and vault checks after each issue.
- **One issue:** `theory/{number}-{short name}` (`-2`, `-3` when the name is taken here or on `origin`) from the default branch, checked out by the plugin. Claude runs in the issue's repository with the permission mode, allowed commands, and the Build row's agent, model and effort, permission cards as step 15a, and `BUILD_SCHEMA` (status, summary, changes, questions, problems). The prompt (`buildPrompt`) holds the snapshot, the issue's repository, number, title, body, rules and branch, and BLD-21's rules (commits end with `Model-Revision:` and `Refs #{n}`). Then `git push -u origin <branch>` (never forced) and `gh pr create` into the default branch, titled like the issue, with Claude's summary and "Closes #{n}".
- **Epic:** `theory/epic-{number}-{short name}`, one name free in every repository with a sub-issue, created from each default branch and pushed. Sub-issues run one at a time in plan order: a branch from the epic branch (brought up to `origin` first), Claude, push, a pull request into the epic branch ("Part of #{epic}" and "Resolves #{n}", with `owner/name#` when the epic's GitHub repository differs, compared by GitHub name; `issueRef` follows BLD-26 and never writes a bare `#n` for another repository), `gh pr merge --merge`, then `gh issue close --reason completed`. Nothing is ever merged into a default branch. At the end: "Epic #{n} is built on {branch}. Open a pull request into {default} when you're ready." (only when a sub-issue is built) and Create PR (W11). A build that skipped sub-issues still finishes, and `build.skippedLine` says "Skipped and still open: {issues}." (BLD-28); with every sub-issue skipped, no epic branch has commits, so there is no Create PR.
- **An issue fails** when Claude reports failed, gives no structured answer, can't start or isn't signed in, changes the snapshot, switches branch, makes no commits, or the push, pull request, merge or close fails. The report then asks: Retry (same branch), Skip (sub-issues only: the issue stays open, its branch stays) or Stop (issues not built stay open).
- **Cancel** stops Claude, then asks Keep branch or Delete branch for the issue being built (Delete removes it locally and on `origin`). Issues not built stay `waiting` and open.
- **State:** `report.build` (status running, finished, stopped or cancelled; the epic branches; the question waiting; the message), each issue's `build` (waiting, building, built, skipped, failed) and `branch`, and every pull request in `report.pullRequests`. Claude's changes, questions and problems join the report's, prefixed with `[repo#n]`. Obsidian closing mid-build: on the next load the issue being built is failed with "Obsidian closed before this issue was built." and its branch stays.
- **Never:** writes to the vault, moves the marker, pushes with force, merges into a default branch, or deletes a branch the engineer didn't choose to delete. Hooks: `build-start` and `build-end`.

## 7. Invariants (must always hold)

1. **The AI never writes to the model.** This is enforced by: the read-only snapshot outside the vault, `--disallowedTools` on the vault and the snapshot, the snapshot hash check (the compile fails if it changed) and the vault working-tree check (it reports changed files).
2. **Only committed revisions are compiled.** The snapshot is `git archive HEAD`, not the working tree.
3. **Every model revision has a human author.** Commits use the `user.name`/`user.email` git uses: the vault's own config, else the global one. A commit fails when either is missing. The settings never edit them.
4. **One compile or build at a time per app instance** (`compileRun` and `buildRun` lock).
5. **The marker moves once Claude has run, whether it succeeded or failed. It never moves on cancel, when compile can't start, when the CLI can't be launched, or when Claude Code isn't signed in.** Failed revisions are not retried by themselves. Re-applying them is a human decision.
6. **Reports live only in plugin data**, which git ignores. The last 20 are kept.
7. **Failure overlays are display only.** They are built from checked anchors, set with `setText` or as attributes (never as HTML or Markdown), and only stored in plugin data.
8. **Claude's text never goes into a note.** Not from a compile, not from a suggestion. Accept on a suggestion only copies it to the clipboard; the engineer writes the note.
9. **Code commits link back to the model** through the `Model-Revision: <vault commit>` trailer. Claude adds it because the prompt tells it to.
10. **A compile only plans.** It never changes a code repository: no file, commit, branch or push. Only a build changes code, on branches the plugin makes, never Claude. Code reaches a default branch only through a pull request a person merges.
