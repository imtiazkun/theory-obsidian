# theory.md — App Workflow (LLM reference)

This file describes how the theory.md Obsidian plugin works. It is written so an LLM can reason about the app. Each step lists its trigger, what it checks first, what it does and what comes out. The source of truth is the code in `src/`. If this file and the code disagree, the code wins.

## 1. One-paragraph summary

theory.md is a desktop-only Obsidian plugin (plugin id `theory-md`). Humans write a **theoretical model** of a software system as notes in an Obsidian vault. The vault is a git repository. Humans **commit** changes to the model as signed git commits. **Compile** sends every commit made since the last compile to the Claude Code CLI. Claude Code then changes the code in a separate **project folder** to match the model. Claude returns a structured **compile report** (summary, changes, questions, problems), which the plugin shows in Obsidian. The AI never writes to the model.

## 2. Glossary

| Term | Meaning |
| --- | --- |
| Vault | The Obsidian vault folder. It holds the model and is its own git repo, on branch `main`. |
| Model / theoretical model | The Markdown notes and assets in the vault. Humans write them. Read-only for the AI. |
| `Index.md` | Entry note at the vault root. Opened on app launch only when Graph view is off. |
| `instruction.md` / `instructions.md` | File at the vault root with the human-only rules and the writing syntax rules. For humans; not sent to Claude and not required for compile. |
| Model folder | A folder at the vault root named exactly like a repository in the project folder. Its notes describe that repository only. It has its own `index.md` and `instructions.md`; that `instructions.md` holds rules for Claude about the repository and is sent (only the root one isn't). |
| Issue | A GitHub issue a compile creates in one code repository. It says what to build and why, and lists the rule IDs it covers (its acceptance criteria). Kept in the report as an `IssueRecord` (`src/plan.ts`). |
| Epic | A GitHub issue labelled `epic` whose native sub-issues are a compile's issues, in build order. A compile plans one when its work spans several repositories or intents. |
| Build | Turns one compile's issues into code (W12). The only step that changes code. |
| Compile branch | A branch a build makes in a code repository, named `theory/…`: an issue branch `theory/{issue number}-{short name}` or an epic branch `theory/epic-{epic number}-{short name}`. Open until it is merged into its base or its pull request is closed. |
| Project folder | Folder that holds the code. It is one git repo, or a folder whose direct subfolders are git repos. A build's Claude runs in the issue's repository here. |
| Code snapshot | A read-only temp folder (`theory-code-*`) with each repository's default branch as `origin` has it, one folder per repository. A compile's agent runs and reads only here (CMP-84). |
| Revision | A git commit in the vault repo. |
| Last compile marker | With Share compile reports on (the default): the `to` of the shared report in `.compiles/`, committed or not, with `markerMoved: true` whose `to` comes last in the vault's history (`markerCommit`, REP-49); the tag is never read. With it off: the local tag `theory/compiled`, as before shared reports (CFG-44). |
| Pending revisions | Commits in `marker..HEAD` that change more than dot folders. With no marker, all commits up to `HEAD`. |
| Snapshot | A read-only copy of the vault at `HEAD`, made in a temp folder (`$TMPDIR/theory-model-*`). Claude reads the model from here. It leaves out the files never sent to Claude (`NOT_SENT` in `src/compile.ts`): dot folders, hidden folders, hidden notes (name starts with `_`, like `_welcome.md`) and `Instructions.md`. |
| Hidden folder | A folder whose name starts with `_`, at any depth, like `_templates`. Committed, but never sent to Claude. |
| Dot folder | A folder whose name starts with `.`, at any depth, like `.obsidian/` or `.comments/` (`DOT_FOLDERS`, `isInDotFolder`). Never sent to any agent, never counted as a change (`changedFiles`), left out of the vault check, and a revision that changes only dot folders is never pending (`pendingRevisionCount`, `revisionsBetween`). theory.md commits `.comments/` itself; git ignores `.obsidian/`. |
| Compile report | JSON record of one compile run. Kept in plugin data. A compile Claude ran also has a shared report, `.compiles/{UTC start}-{short id}.json`, and its Activity log, `.activity.log` beside it. Never in the model. |
| Plugin data | `.obsidian/plugins/theory-md/data.json`. Holds the settings, every shared report this machine compiled or worked on and the last 20 that aren't shared, with permission answers and pull request states. A teammate's report from `.compiles/` joins it once this machine builds, recompiles or opens pull requests for it (REP-50). Git ignores it. |
| Anchor | Where a problem sits in the model: `{path, heading?, quote?}`. Claude proposes it, and the plugin checks it against the snapshot before keeping it. |
| Realized | Front matter `realized: false` marks a note as written ahead of the code. If the key is missing, the note counts as realized. Engineers set it with a box in the note header. |
| Failure overlay | Highlights and a banner the plugin draws on notes that a failed compile points to. Display only: it never edits a note. |

## 3. Actors and components

- **Engineer** (human): edits notes, commits, clicks Compile, reads reports, answers questions by editing the model.
- **Plugin** (`src/main.ts`, class `TheoryPlugin`): wires commands, views, buttons and events, and holds the compile lock.
- **Git** (run as a subprocess through `git()` in `src/vault.ts`): stores the model's history, the shared reports that set the marker, diffs and snapshots.
- **Claude Code CLI** (run as a subprocess in `src/compile.ts`): reads the snapshot, edits the project folder, runs the allowed commands and returns structured output.
- **ACP agent** (optional, run as a subprocess in `src/acp.ts`): when the Compile or Build row's agent is "ACP agent", that task runs the engineer's own Agent Client Protocol agent (e.g. `gemini --experimental-acp`) instead of Claude Code. Expand and Writing (Suggest, commit messages and pull request bodies) always use Claude Code. The plugin never installs an agent.

Remote is a setting too, but it isn't in plugin data: it is the vault's `origin` in its git config. When the vault has an `origin`, the setting shows its URL as plain text with no field, and says to run `git remote set-url origin <url>` in the vault to change it. Without one, Save runs `git remote add origin <url>`, then a pull. Save never replaces or removes a remote. It refuses an empty URL, spaces, a leading `-` and a password or token in an https URL.

## 5. Lifecycle state machine (per vault)

```
UNCONFIGURED ──(Setup vault)──► VAULT_READY ──(set projectFolder)──► COMPILE_READY
                                                                         │
            ┌──────────────── edit note ◄───────────────────────────────┤
            ▼                                                            │
         DIRTY ──(commit)──► PENDING (n > 0 revisions) ──(Compile)──► COMPILING
                                                                         │
                       ┌─────────────────────────────────────────────────┤
                       ▼                   ▼                    ▼
                  SUCCEEDED             FAILED              CANCELLED
              (marker → HEAD)       (marker → HEAD)      (marker unchanged)
```

Compile button states (`src/compile-button.ts`, `readState`), checked in this order:
1. `hidden`: the vault isn't set up, or the button is turned off.
2. `running`: a compile is in progress. While a permission card waits, it says "Claude is asking (1:47)", counting down with the oldest card, and clicking it opens the report at that card.
3. `setup`: no project folder is set.
4. `ready(pending)`: there are pending revisions. Shows a badge with the count, in the accent colour.
5. `failed`: no pending revisions, and the newest report failed.
6. `idle`: nothing to do.

## 6. Workflows

### W1. Plugin load (`onload`)
1. Load the settings and reports from plugin data. Any report still marked `running` becomes `failed` with the problem "Obsidian closed before this compile finished."
2. Register exactly the commands in `THEORY_COMMANDS` (`src/commands.ts`, UI-10): `setup-vault`, `show-commit-history`, `compile`, `build`, `show-compile-report`, `commit-current-note`, `show-repositories`, `pull-now`, `comment-on-selection`, `show-comments`, `use-core-plugins` and `new-repository`, plus the one ribbon button in `THEORY_RIBBON` (Repositories, UI-8) and a status bar item. There is no Compile ribbon button (CMP-1).
3. When the layout is ready: add the commit history, compile history and Comments views to the right sidebar, then, once per launch, set up the launch layout (`src/launch.ts`): both sidebars expanded, the file explorer on the left, the Comments view as the right sidebar's active tab, and Graph view as the active tab (the one restored from the last session, else a new one; the other tabs stay open behind it). When the Graph view core plugin is off, `Index.md` opens instead, or no tab when there is none. It never runs when the plugin is turned on mid-session, when the vault is reopened in the same window (or the window reloads), or on focus. Then sync the commit buttons and attach and refresh the compile bar, and run the first load when install.sh asked for it, so Setup vault's note opens after Graph view. On launch, pull (W14) and start the pull timer.
4. Event hooks: vault `modify/create/delete/rename`, workspace `layout-change/file-open` and window `focus` re-sync the buttons and the pending count (debounced).

### W2. Setup vault (command "Setup vault")
- **Check first:** the vault isn't already a git repo (no `.git`). Git runs and has a name and email (`gitIdentity`: the vault's `--local` config, else `--global`). Otherwise it fails with a notice.
- **Actions:** write the starter files from `src/starter.ts` if the root doesn't already have them under any name, ignoring case: `Index.md` ("Manifesting <vault name>"), `Instructions.md` (the human-only rules and the doctrine, skipped if `instruction.md` or `instructions.md` exists), `_templates/index.md` (the model folder index headings) and `_templates/instructions.md` (the line pointing at the root Instructions). Then, when the root has `Welcome.md` (ignoring case) and no `_welcome.md`, replace its text with the welcome text (`WELCOME_TEXT` in `src/starter.ts`) and rename it to `_welcome.md`; it is not a starter file, so Create missing files never writes it back. Then `git init -b main`, then add the missing lines to `.gitignore` (`.DS_Store`, `.trash/`, `.obsidian/`), then `git add -A`, then `git commit --allow-empty -m "Initial commit"` signed with the author.
- **Output:** the vault is a git repo whose initial commit includes the starter files and the welcome note. The UI refreshes and `_welcome.md` opens when setup wrote it, `Index.md` otherwise, as the active tab; when Graph view is the active tab, the note opens in a new tab after it.
- **Create missing files** (settings, when the vault is set up but `missingStarters` finds starter files or `.gitignore` lines missing): checks the author, writes only the missing files and lines with the same starter text, never changes a file that exists, and commits only what it wrote as "Add missing starter files". The check runs each time the settings tab opens and after the button runs; nothing is stored.

### W2a. First load (SET-20 to SET-25)
- **Trigger:** `setupOnLoad: true` in plugin data, written by `scripts/install.sh` on a first install only. Installing by hand or through BRAT has no request (SET-25). Runs once, when the layout is ready (`setUpOnFirstLoad` in `main.ts`, through `runFirstLoad`).
- **Order:** drop the request from plugin data (if that save fails, nothing runs), then step 1, then step 2. Step 1 failing never stops step 2 (SET-24).
- **Step 1** (`useTheoryWorkspace` in `src/workspace-setup.ts`): turn on exactly `command-palette`, `file-recovery`, `file-explorer`, `graph`, `note-composer`, `page-preview`, `switcher`, `global-search`, `templates` and `word-count`, and turn off every other core plugin, at once with no reload (SET-21). A plugin that can't be changed is skipped. Notice: "theory.md turned off {n} core plugins it doesn't use. Turn any back on in Settings → Core plugins." plus "Couldn't change: {plugins}." (SET-22, SET-24); none when nothing changed. Then the left ribbon order, top to bottom: Open graph view, Open quick switcher, Insert template, Open command palette, Repositories, then every other button in Obsidian's order (UI-43); when the ribbon can't be read or saved it stays in Obsidian's order (UI-44). Then Graph view's colour groups, first and in this order: `path:_templates/` grey, `file:/^index\.md$/` blue, `file:/^instructions\.md$/` green. A group whose query is there already keeps the engineer's colour; every other group is kept after them (UI-36 to UI-38). A `graph.json` that can't be parsed is never overwritten.
- **Step 2:** Setup vault (W2). A vault that already has git is left as it is, and the notice names the missing starter files and `.gitignore` lines.
- **Never again:** core plugins, the ribbon and the colour groups are never checked or changed after this (SET-23), except by the command "Use theory.md's core plugins", which runs step 1 after asking "Turn off every core plugin except {list}?" (SET-25).

### W3. Edit and commit
- **Trigger:** the commit button in a note's header (marked `is-dirty` when the note has changes), the commit button in the floating bar, or the command "Commit current note".
- **Check first:** the note is in the list of changed files (`git status --porcelain -z --untracked-files=all`). If not, the notice "No changes to commit in this note." The floating commit button commits the active note when it has changes, else every changed file, else shows "No changes to commit".
- **Commit page:** opens in a new tab, never a modal; only one page for new changes is open, and another commit brings it to the front. It lists every changed file with a checkbox, its path and how it changed (modified, new, deleted, renamed). A commit from a note ticks only that note; from the floating bar with no note changed, every file. Under each file its diff from `git diff HEAD -U3` (new untracked files through `git diff --no-index /dev/null`), removed lines red, added green, unchanged stretches between hunks folded into "{n} unchanged lines". Above a note's diff, "Adds X. Changes Y. Removes Z." from the bold rule IDs before and after. A rename shows "{old} → {new}"; a file that isn't text shows only its name and kind. The diff is raw text set with `setText`, and refreshes when a file changes. The message box starts empty with the placeholder "Say why. Git already shows what changed."; Commit stays disabled until it holds text and a file is ticked. "Signed as Name <email>". Cmd/Ctrl+Enter commits; Cancel closes the page and discards the message.
- **Generate (sparkle):** the uncommitted diff of the ticked files (tracked files against `HEAD`, new files whole, minus dot folders, hidden folders, hidden notes and `Instructions.md`, cut at 50,000 characters) goes on stdin to `claude -p --output-format json --no-session-persistence --tools ""`, run in the temp folder, with Edit/Write/NotebookEdit denied on the vault, and the Writing row's `--model` and `--effort`. While Claude writes, the sparkle blinks (fades out and back in about once a second); it never spins and no bar shows. The answer replaces the message. It sends uncommitted text, but never compiles it. On failure: "Couldn't generate a message: {reason}".
- **Actions:** `git add -A -- <ticked paths>` (a deletion that is already staged is skipped, since git refuses its path) then `git commit -m <msg> -- <ticked paths and the old side of a staged rename>`, so nothing else that is staged slips in. It uses `-c user.name/-c user.email` with the identity `gitIdentity` reads, so what the settings and the page show is what signs. With no name or email the notice is "Set your name and email in git first. theory.md settings show how." and nothing is committed.
- **Push:** straight after, `git push --no-tags origin refs/heads/main:refs/heads/main` with prompts off. Never forced, never with tags. Every other commit the plugin makes (comments, shared reports, missing starter files) pushes the same way. Pushes run one at a time.
- **Output:** the page closes, and the notice "Committed and pushed {shortHash}"; "Committed {shortHash}" without an `origin`; "Committed {shortHash}, but couldn't push: {reason}" when the push fails (the commit stays, and the sync status counts what isn't pushed); "Committed {shortHash}, but couldn't push: the remote has new revisions. Pull with rebase in git, then push." when the remote moved. The buttons, the pending count, the sync status and the history view refresh.
- **Past commits:** clicking a commit in commit history opens it read-only on the Commit page, in its own tab that the next click reuses: full message, author, date, short hash, then every file the commit changed with its own diff against its first parent (the empty tree for the first commit), the clicked note first. No checkboxes, message box or Commit button.

### W4. Compile (the core pipeline)
**Trigger:** the compile button, the command "Compile", or Recompile in a compile report (CMP-1, `TheoryPlugin.recompile(reportId)`, the only way to start a recompile, CMP-72).

**Recompile in the report** (`recompileButton`, drawn next to Build in "Build them now?" and in the build row). It shows for a succeeded compile that created issues while `recompileBlocker` finds nothing (CMP-73): no recompile of it succeeded or changed an earlier issue on GitHub (`!canDiscard`), no later compile succeeded, no issue has a recorded build branch, no epic branch was recorded and no pull request was opened. It is disabled with the tooltip "Commit your answers to the model first." while no revision is pending (CMP-74; the view counts them with `pendingRevisionCount` on each draw), and while a compile or build runs. A recompile runs every check below, with "Recompile failed:" in place of "Compile failed:" (`startFailure`, CMP-75).

**The two reports are linked** by the recompile's `recompileOf` (the earlier report's id) and `earlier` (its date and revision range), both in plugin data; the shared reports link each other's files with `recompileOf` and `recompiledBy` (REP-45). `recompiledBy(report, reports)` finds the recompile that took a compile's issues over: one that succeeded, or that changed an earlier issue on GitHub. The recompiled compile's report then says "Recompiled on {date}" with a link, offers no Build and no Recompile, and marks each issue "continued" or "closed" (`issueFate`, REP-41). The recompile's report says "Recompiles the compile of {date}" with a link, marks each issue "new" or "continued" (`issueOrigin`), and lists the closed ones after them (REP-42). `buildableReport` and `startBuild` never build a recompiled compile (CMP-83). The `compile-start` and `compile-end` hooks of a recompile add `recompile: true`, `earlier` (date, from, to), and `compile-end` the lists `created`, `continued` and `closed` (`compileStartDetails`, `compileEndDetails`, HOOK-3).

**Phase A: checks in `main.ts`** (if one fails, it shows a notice and does nothing else)
1. If a compile or build is already running (or starting), show "A compile or build is already running." and open the report. This is an in-memory lock, one compile or build per app.
1a. Pull the vault and the code repositories (W14), even with automatic pulls off. A sync needed or waiting revisions stop the compile with "Compile failed: …". A code repository that is behind, on any branch, never stops it (PULL-16): the compile reads `origin`'s default branch, not the checkout (step 10a). A build checks its own default branches (BLD-7). A failed fetch shows "Couldn't reach the remote, so this compile uses the local vault and code. Code is read as of the last fetch." and carries on. `main.ts` passes the paths of the repositories this pull fetched as `fetched`.
2. The vault must be set up.
3. Count the uncommitted files and warn that they aren't part of this compile. Only committed revisions are compiled.

**Phase B: start-up in `startCompile`** (if one of these throws, the compile doesn't start and the marker doesn't move)

The `theory/compiled` tag is never read, except with Share compile reports off (`options.shareReports: false`), when the tag is the marker (CFG-44).
7. If `from === head`, or every revision in `from..head` changes only dot folders, it throws `NothingToCompileError` ("Every committed revision is already compiled.").
7a. Every repository in the project folder must have a clean working tree (`git status --porcelain`), else "These repositories have uncommitted changes: {repos}. Commit or stash them first."
7b. GitHub (`requireGitHub`, with the `GitHub` interface in `src/github.ts`; tests pass a fake): `gh` must be logged in ("Log in to GitHub first. Run gh auth login in a terminal."), every repository must have a GitHub `origin` ("These repositories have no GitHub origin: {repos}."), and the GitHub Project setting must be set ("Choose the GitHub Project in theory.md settings first.") and reachable with `gh project view` ("Couldn't reach the GitHub Project {url}: {reason}").
7c. In a recompile, CMP-73 again (`recompileProblem`, with `options.reports`): `recompileBlocker`, then whether `theory/{n}-{short name}` or the epic's `theory/epic-{n}-{short name}` exists for any of its issues, locally or under `refs/remotes/origin/`, the `-2`, `-3` names of BLD-12 included (`buildBranch`). A reason throws, shown as "Recompile failed: {reason}" (CMP-75), and the marker stays.
8. `revisions` = `git log --reverse from..head -- <DOT_FOLDERS>` (hash, author, ISO date, subject), so revisions that change only dot folders aren't listed.
9. `diff` = `git diff --stat --patch <from or EMPTY_TREE> head -- <NOT_SENT>`, cut at 200,000 characters. `notes` = the `.md` files changed in that range (`git diff --name-only`, same pathspecs), kept as suspects for the overlay. `NOT_SENT` excludes dot folders, hidden folders, hidden notes and `Instructions.md`.
10. Record each repository's HEAD, branches and working tree, to check afterwards that the compile changed none of them (CMP-69). A compile never makes a branch, a commit or a push.
10a. **Code snapshot** (`createCodeSnapshot` in `src/code-snapshot.ts`, CMP-84 to CMP-88). For each repository: the default branch is the one GitHub names (`GitHub.defaultBranch`, `gh repo view --json defaultBranchRef`); when GitHub can't answer, the one `origin/HEAD` points at, else the local default branch (`defaultBranch`). The copy comes from `refs/remotes/origin/{branch}`: source `origin` when this pull fetched the repository, `last-fetch` when it didn't (CMP-87). A repository with no `origin/{branch}` (never fetched) is copied from its local `{branch}` (source `local`). `git archive <commit>` into `$TMPDIR/theory-code-*/{repo name}/`, then `chmod -R a-w` on the whole folder. Only `git rev-parse` and `git archive` touch the repository: no checkout, switch, stash, new ref or config change (CMP-85), so nothing unpushed or uncommitted is in it (CMP-86). When the branch can't be found or `git archive` fails, the folder is deleted and it throws "Couldn't read {branch} of {repo}: {reason}", shown as "Compile failed: …", and the marker stays (CMP-88). What each repository was read at (`CodeRead`: repo, branch, commit, source, GitHub commit `url`) goes in `report.code` (REP-43).
10b. Snapshot: `git archive head -- <NOT_SENT>` into a new temp folder, extract it, then `chmod -R a-w`. If this or the next step throws, both snapshots are deleted.
11. Record the guards: a SHA-256 hash of the snapshot tree, the same hash of the code snapshot (INV-14), and the vault's working-tree state (path → mtime, or "deleted").
11a. Read each repository's model-folder `instructions.md` from the snapshot (matched ignoring case) for the prompt.
11c. **Recompile** (`options.recompile`, an earlier report; CMP-76). `from` for steps 8 and 9 (revisions, diff, suspect notes) is that report's `fromCommit`, not the marker, so they cover its revisions and every pending one; the new report's `fromCommit` is the same, and `recompileOf` is the earlier report's id. `openEarlierIssues` asks GitHub (`issueState`) about each of its issues that has a number and wasn't discarded, and keeps the open ones for the prompt and `readPlan`; when GitHub can't answer, the compile can't start. The pending check still uses the marker.

**Phase C: run Claude Code**
12. Make the report `{status: "running", fromCommit, toCommit: head, revisions, …}`, add it to the front of `reports` (keep 20), save, open the report tab and show "Compiling…" in the status bar.
13. Start `claudeCommand` with `cwd = <code snapshot>` (CMP-13) and these arguments (`claudeArgs`, `startSession`):
    - `-p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio --verbose --no-session-persistence`
    - `--permission-mode dontAsk --tools Read,Glob,Grep --strict-mcp-config`: a compile only reads (CMP-13)
    - `--add-dir <snapshot>`
    - `--json-schema <COMPILE_SCHEMA>` (fields: `status`, `summary`, `plan{epic?{title, body, rules[], shortName, continues?, changed?}, issues[{repo, title, body, rules[], shortName, continues?, changed?}]}`; `continues` is the number of the earlier issue it continues in a recompile, `changed` the CMP-79 sentence, `questions[{question, notes[], anchors?[{path, heading?, quote?}]}]`, `problems[{problem, anchors[{path, heading?, quote?}]}]`)
    - `--disallowedTools Edit/Write/NotebookEdit(//<vault>/**)` and the same for `//<snapshot>/**` and `//<code snapshot>/**`, then `Edit Write NotebookEdit MultiEdit Bash`
    - `--model <model>` and `--effort <effort>` when they aren't empty. They're fixed when Claude Code starts, so a running compile keeps them.
    - `--allowedTools Read Glob Grep`. The Permission mode and Allowed commands settings apply to builds only.

The prompt goes in through stdin (`compilePrompt`) as a stream-json `user` message, after an `initialize` control request: the snapshot's path, the repositories, the code snapshot's path and what each repository was read at ("api: main at 098e623", with "(origin/main as of the last fetch)" or "(the local main: it was never fetched)" for CMP-87), the rules of CMP-12 (read the code only in the code snapshot, never change a file, plan one issue or an epic with sub-issues in build order, one repository per issue, rule IDs as acceptance criteria, titles and short names as CMP-61 and CMP-62 say, in a recompile continue an earlier issue whenever the same work is still asked for in the same repository (CMP-77), never touch GitHub), then each model folder's `instructions.md`, then, in a recompile, the earlier compile's start and its open issues (number, repository, kind, title, body, rules, short name), then the revisions and the diff.

The `result` event holds `structured_output`, and its `usage` is added to `report.tokens` in four parts (`input`, `output`, `cacheWrites`, `cacheReads`, with `model`; REP-56). A build's go to `report.build.tokens` instead (`usageTo`), never to the compile's.
15a. **Permission requests.** A compile never shows a card: every `can_use_tool` request is denied at once, logged as "Denied: {command}" and named in problems ("A compile only reads, so …"). The rest of this step is how a **build** (W12) handles them. A tool call the settings don't allow arrives as a `control_request` with subtype `can_use_tool`; it's never refused without asking. An Edit/Write/NotebookEdit/MultiEdit on a file inside the vault or the snapshot is denied at once, with no card. Anything else becomes a `PermissionRequest` (tool, the exact command or file, Claude's reason: the tool's `description`, else `decision_reason`) shown as a card in Activity, on the log line where Claude asked (`PermissionRequest.line`, kept in step as old lines drop off), with a Notice. While a card waits, Activity is open and scrolled to the oldest card. The Deny button counts down the time left, from "Deny (2:00)" to "Deny (0:00)". Each card has its own 120-second timer and is answered on its own: **Allow** (allow once), **Always allow** (allow, add the request's rules (`PermissionRequest.rules`) to the session through `updatedPermissions`, and append them to the `allowedTools` setting; the rules follow CFG-16: for a command, every rule Claude Code suggests for Bash in the request's `permission_suggestions`, e.g. `Bash(npm run:*)` (a compound command like `cd app && npm test` may get one per part, and all are added), else the exact command, e.g. `Bash(npm run build)`; for a file tool (Edit, Write, NotebookEdit, MultiEdit), that tool on that exact absolute file, e.g. `Edit(//Users/me/.zshrc)`, never the bare tool name or Claude Code's suggestion, and no Always allow button when the request names no file; for any other tool, Claude Code's suggestion, else the tool's name; the card shows every rule before the click; they go at the end of the list and none is ever added twice) or **Deny**. No answer in 120 seconds denies it. A `control_cancel_request` withdraws the request: its timer stops and its card becomes "Withdrawn: {command}", kept in the log but not a problem, because nobody refused it.

The agent command is split into words (quotes kept together) and started with `cwd` = the session's folder: the code snapshot in a compile (CMP-13), the issue's repository in a build. Every `session/request_permission` becomes a card like 15a, except a request of kind edit, delete or move on a vault or snapshot file, which is rejected at once with no card and named in problems. Buttons go back as the agent's options: Allow → `allow_once`; Always allow → `allow_always`, else `allow_once`; Deny (and a timeout) → `reject_once`, else `reject_always`. Always allow lasts for this compile only and never changes `allowedTools`. `fs/read_text_file` reads any file; `fs/write_text_file` is refused outside the project folder and on the vault or the snapshot (symlinks followed), and each refusal is a problem. Permission mode and Allowed commands don't apply. The report has `agent: "acp"` and no token count. Once the prompt returns, the agent is stopped. In a compile the agent is read-only: `initialize` offers no file writing, every `fs/write_text_file` is refused, a permission request of kind read or search is allowed without a card and every other one is rejected without a card, and the answer must have `plan` instead of `changes`.

16a. On cancel and when the agent couldn't start, the snapshot check, the code snapshot check and the vault check still run and add their problems (AGT-17, INV-12, INV-14), but the status stays as it is and the marker doesn't move.

If there is structured output, copy it into the report, but keep its `problems` aside for step 21. `status = succeeded` only if Claude said `succeeded` and the result isn't an error. Leading `./` is removed from note paths. A succeeded answer's plan is read by `readPlan` (CMP-70): one issue, or an epic with at least two sub-issues (kept in Claude's order, the build order); every repository in the project folder; every issue, the epic included, lists at least one rule ID; short names of lowercase letters, digits and dashes, at most 40 characters, and no two the same in one plan, the epic's included; titles under 70 characters. A plan that breaks these fails the compile with each reason in problems, each naming the issue it is about by its title (by its short name when it has no title). A plan with no epic and no issues has nothing to build (CMP-71); an epic with no sub-issues is a broken plan, not an empty one. In a recompile `readPlan` also checks CMP-78 against the earlier compile's open issues: each `continues` names one of them, an issue continues an issue (a sub-issue counts) in the same repository, an epic continues an epic (its repository isn't checked: CMP-64 keeps it where it is), and no earlier issue is continued twice. Outside a recompile, any `continues` fails the plan.

If there is no structured output, `status = failed` and the problems always get "Claude Code exited with code N." and stderr (for an ACP agent, never the exit code: "The agent gave no structured answer. It stopped because: {reason}." with the stop reason or the error that ended the turn, then the end of stderr; AGT-22).

Then run `checkProblems` on Claude's problems: the text is cut to 2,000 characters, and an anchor is kept only if its path resolves (after following symlinks) to a file inside the snapshot. Its heading and quote are kept only if they appear in that file, and at most 5 anchors are kept per problem. If the snapshot changed, every anchor is dropped, `status = failed`, and the problem "Claude tried to change the model snapshot…" is added. The code snapshot is hashed again too: if it changed, every anchor is dropped, `status = failed`, and the problem "Claude tried to change the code snapshot. Those changes were thrown away." is added (INV-14). Each question's anchors go through the same check (`checkAnchors`); a question keeps `anchors` only when at least one survives.

21b. On failure, no issue is created and the marker moves (step 22). On success with an empty plan, nothing is created, `report.issues` is empty, `status = succeeded` and the marker moves (CMP-71). Otherwise the snapshot is removed, then the plugin creates the plan on GitHub (`createIssues`): the epic first in the repository with the most sub-issues (the first by name on a tie), after creating the `epic` label there when it is missing; then each sub-issue in its own repository, linked to the epic as a native sub-issue (`gh api …/sub_issues`); every issue added to the GitHub Project (`gh project item-add`). The new plan is {epic's address, or the issues' addresses}." (with an empty plan: "The model no longer asks for this work ({short})."), then close as not planned. An empty plan with nothing to close is CMP-71. Each step is saved in the records as it is done. When one fails, `issueFailure` names the step ("Couldn't create the issues", "Couldn't update the continued issues", "Couldn't link the sub-issues", "Couldn't close the earlier issues") and the report lists `stepsLeft`; Retry carries on from there. Discard (closing only the new issues, never a continued one) is offered while `canDiscard`: no continued issue touched and no earlier issue commented on or closed. After that, Discard does nothing, and Cancel stops the recompile (cancelled, nothing closed, the marker in place, the steps still to do in its problems). The marker moves once every step is done (CMP-81). Build then builds the new report's issues in the new plan's order (CMP-83).

When the compile ends, `compileMoment` picks: nothing when Claude never ran or it was cancelled before it was shared; "Recompile {earlier short id}" for a recompile, holding both reports (the earlier one gains `recompiledBy`); "Update compile {short id}" when it was shared already; else "Compile {from short}..{to short}" (`start` on the first compile). ### W5. Cancel a compile
`cancelCompile()` denies every open permission request, then sends SIGTERM to the Claude process if the report is still running. With an ACP agent it answers every open request as cancelled and sends `session/cancel`; an agent still running 5 seconds later gets SIGTERM. The result is `cancelled` and the marker stays where it was. Unloading the plugin also cancels.

### W6. Read the report and answer questions
The report tab lists reports newest first, in a dropdown with the compile history's list (`listReports` in `src/report-list.ts`, REP-51): the reports in plugin data and every file in `.compiles/` together, ordered by start time. A shared report this machine has in its data file is listed once, as that report; every other shared report is read from its file and has its file as its id (`fromSharedReport`). Each line is "{start} · {status}", then who compiled a shared report, or "Only on this machine" for a report that is only in the data file (never shared, its last commit or push failed, or its file is gone). A file that can't be read is "Can't read {file}" (REP-52), sorted by the start in its name; it is never overwritten and never counts for the marker. `.compiles/` is read on layout ready, when the report or the compile history opens, after a pull that brought revisions, and after each share; that read also takes into this machine's shared reports what teammates added (`absorbSharedFiles`). Each report then shows: status, the commit range `from..to`, revisions, summary, changes, questions (each links to the model notes it names and has a **Reply** button that opens the note at the rule that needs updating: its first checked anchor's quote, else that anchor's heading, else the top of the note; with no anchor, the top of its first note), problems and the tool log ("Activity", folded until opened, except while a permission card waits). A report from `.compiles/` (`fromShared`) shows Activity from its `.activity.log`, then the lines this machine's builds of it added; with no log file, or one that can't be read, it says "No activity log was shared for this compile." (REP-54). Under the status line, the report says "Compiled by {name}" or "Only on this machine". Sections with nothing in them are left out.

**Working on a teammate's report (REP-50).** Build, Recompile and Create PR work on any listed report. A report read from `.compiles/` joins plugin data first (`adoptReport` in `main.ts`), so its build, pull requests and permission answers are kept; it is shared, so the data file never drops it. Its issue bodies aren't in the shared file, so a build (`startBuild`) and a recompile (`openEarlierIssues`) read the bodies they need from GitHub (`issueBody`, then `plannedBody` takes off the rules and revisions the plugin added; `fillIssueBodies`). Its epic branch is the base of a sub-issue's pull request, else `theory/epic-{n}-{short name}`, with the default branch the compile read as its base, so a teammate's build continues on the same epic branch. Before writing to a report that is shared already (a build, Create PR, Retry or Discard, the earlier report of a recompile), `shareReport` pulls the vault (`ctx.pull`, the Puller's `share` reason; never during a compile, PULL-4). When the pull can't fast-forward (diverged, or revisions waiting) and that report's file changed on `origin/main` since the two parted (`changedOnRemote`), nothing is written and the notice says "Someone else changed this compile. Pull with rebase in git, then try again."; the report keeps `notShared`, so its next commit carries the change. Otherwise it takes in the file's builds (by who and when), pull requests (by URL, new ones count as open until GitHub is asked) and, when a teammate's build is newer than this machine's, that build's issue states and record (`absorbShared`), then writes. Links to reports this machine doesn't list are kept (`sharedLinks`).

**Two engineers compiling at once (CMP-91, CMP-3).** The compile lock is per machine. When a compile's shared report (moments Compile, Update or Recompile) can't be pushed because the remote moved, `compiledMeanwhile` fetches and reads `.compiles/` on `origin/main`. When the report that sets the marker there moved it past this compile's `from` (onto a descendant of it, or anywhere on a first compile), `report.compiledMeanwhile` names that file, the notice and the report say "Someone else compiled these revisions while you did. Check both reports before you build.", and the compile keeps its issues. The report stays committed locally, not pushed, as REP-48 says.

**Upgrading to shared reports (CFG-45).** On the first load with shared reports (`settings.markerImported` unset), after the launch pull, `importMarkerOnce` in `main.ts` runs `importMarker` while Share compile reports is on. It reads the local tag `theory/compiled`; with no tag, or when `.compiles/` already has a report with `markerMoved: true` (committed or not), it writes nothing. Otherwise it writes one marker-only shared report (`importedReport`: `from` and `to` the tag, `markerMoved: true`, status `imported`, shown as "Imported", summary "Marker carried over from {author}'s machine", the author from git, no agent, revisions or issues), commits only it as "Share the compile marker", signed by git's identity, and pushes. A failed commit deletes the file and the import runs again on the next load; a failed push gives the REP-48 notice "Compile report saved but not shared: {reason}", and the commit stays to go with the next push. Reports already in plugin data stay there and list as "Only on this machine". The tag is left in place and isn't read while sharing is on. When two engineers upgrade with different tags, the later `to` wins (REP-49), and whoever pushes second gets the REP-48 notice. A compile started meanwhile waits for the import (`runCompile`).

**Estimated costs (REP-56, REP-57).** Under who compiled, the report shows "Estimated cost: Compile $x", and once a build ran, "· Build $y · Total $z" (`reportCostPieces` in `src/costs.ts`). The compile's tokens are `report.tokens`; the build's are every build of the compile together, each ended one from `report.builds[].tokens` and the latest from `report.build.tokens` until it joins `builds`, each priced at its own model. A cost is the four parts at the model's price per million tokens: the settings' Model prices first, then `BUILT_IN_PRICES`. Hovering a cost shows the model and each part's tokens and dollars. A model on neither list shows "Price unknown" (and makes the total unknown); no tokens show "Not reported" (left out of the total); a report from before REP-56 has one count, `tokens` as a number, shown as "{n} tokens" with no price. The shared file holds the compile's `tokens` and each build's, so teammates see the same costs; a file without them reads as "Not reported".

Below Reply, each question has a **Suggest** button (`src/suggest.ts`). It runs `claude -p --output-format json --tools "" --strict-mcp-config` in the temp folder, with the Writing row's model and effort and the prompt on stdin. The prompt holds only the question, its anchors, the current text of every note it names (read from the vault, uncommitted edits included) and the compile's summary. While it runs the button says "Suggesting…" and is disabled; a question has at most one suggestion. The suggestion shows under the question: the note and heading it is for, the text in an editable box and one sentence on why. **Accept** copies the box to the clipboard, opens the note at the same spot as Reply and shows "Suggestion copied. Write it in the note in your own words." It never writes to a note. **Reject** removes it. A failure shows "Couldn't get a suggestion: {reason}" and Suggest works again. Suggestions live only in the view: never in the report, plugin data or the vault, and closing the report discards them (and stops any still running).

Engineers answer questions by **editing the model, committing and compiling again** (back to W3, then W4). Reports are never written into the vault.

## 7. Invariants (must always hold)

1. **The AI never writes to the model.** This is enforced by: the read-only snapshot outside the vault, `--disallowedTools` on the vault and the snapshot, the snapshot hash check (the compile fails if it changed) and the vault working-tree check (it reports changed files).
2. **Only committed revisions are compiled.** The snapshot is `git archive HEAD`, not the working tree.
3. **Every model revision has a human author.** Commits use the `user.name`/`user.email` git uses: the vault's own config, else the global one. A commit fails when either is missing. The settings never edit them.
4. **One compile or build at a time per app instance** (`compileRun` and `buildRun` lock).
5. **The marker moves once Claude has run, whether it succeeded or failed, when the shared report is written to `.compiles/` with `markerMoved: true`. Committing and pushing it only share the move (CMP-22). Discard writes it again with `markerMoved: false`. It never moves on cancel, when compile can't start, when the CLI can't be launched, when Claude Code isn't signed in, or in a build or pull request.** It is read from the reports in `.compiles/`, committed or not (`writtenSharedReports`; REP-49), never from a tag, unless Share compile reports is off: then the marker is the local tag `theory/compiled`, moved when the compile ends, and nothing is shared (CFG-44). Failed revisions are not retried by themselves. Re-applying them is a human decision.
6. **Reports are never written into the model.** The shared part of a compile Claude ran lives in the `.compiles/` dot folder, which is never sent to an agent; permission answers, pull request states and the reports of compiles that were cancelled, couldn't start or still run live only in plugin data, which git ignores. Plugin data keeps the last 20 reports that aren't shared; shared ones are never deleted.
7. **Failure overlays are display only.** They are built from checked anchors, set with `setText` or as attributes (never as HTML or Markdown), and only stored in plugin data.
8. **Claude's text never goes into a note.** Not from a compile, not from a suggestion. Accept on a suggestion only copies it to the clipboard; the engineer writes the note.
9. **Code commits link back to the model** through the `Model-Revision: <vault commit>` trailer. Claude adds it because the prompt tells it to.
10. **A compile only plans.** It never changes a code repository: no file, commit, branch, push, checkout, stash, ref or config change. Its agent runs in, and reads, only the read-only code snapshot of each default branch as `origin` has it, which is hash-checked and write-denied like the model snapshot (INV-14) and always deleted (CMP-89). Only a build changes code, on branches the plugin makes, never Claude. Code reaches a default branch only through a pull request a person merges.
